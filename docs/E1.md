# Módulo E.1 — Controle de Produtos e Estoque

Somente arquivos do E.1, nas pastas definidas em `docs/architecture.md`. Nada do que o E.2 já escreveu foi alterado.

## Arquivos do E.1
Já existiam vazios no esqueleto (foram preenchidos):
- `domain/product/` Product, Category
- `domain/inventory/` StockMovement, MovementType
- `repositories/` ProductRepository, StockMovementRepository
- `infrastructure/memory/` InMemoryProductRepository, InMemoryStockMovementRepository
- `application/product/ProductService` — cadastro sem código duplicado, pesquisa, edição, filtro, ordenação, categorias
- `application/inventory/InventoryService` — entrada/saída, histórico, alertas, sem movimentação, mais vendidos, baixa por venda
- `presentation/cli/StockistMenu` — menu do estoquista

Novos (na mesma pasta de apresentação):
- `presentation/cli/ProductAdminMenu` — parte do menu do administrador que é do E.1 (produtos, categorias, relatórios de estoque)
- `presentation/cli/StockMenuBase` — leitura validada, consultas e tabelas comuns aos dois menus

Testes e demonstração (`src/test`, fora da arquitetura de produção):
- `E1Tests` (37 testes) e `E1Demo` (executa o E.1 sozinho, com dados de exemplo)

## Não foram usados nem alterados
Main, CliApplication, MenuRouter, AdminMenu, CashierMenu, InputReader, TerminalOutput, todo o checkout/QueueService,
user/*, store/*, sales/* (Sale, SaleItem), SaleService, SaleRepository, DashboardService, AuthService, SupermarketService. O `pom.xml` recebeu apenas o driver MySQL e o plugin de execução (ver LEIA-ME-MYSQL.md).

## Como o E.1 se liga ao resto
1. Menus: `new StockistMenu(scanner, out, productService, inventoryService, nomeDoUsuario).run()` e
   `new ProductAdminMenu(...).run()` (chamar de uma opção do AdminMenu), no MenuRouter/AdminMenu.
   Recebem `Scanner` e `PrintStream`; se preferirem InputReader/TerminalOutput, basta ajustar os métodos de E/S de `StockMenuBase`.
2. Baixa de estoque por venda (E.2 chama o E.1), ao concluir a venda no SaleService:
   `inventoryService.registerSaleExit(dataDaVenda, List<InventoryService.SoldItem>, nomeOperador)` (tudo ou nada).
   Antes, o carrinho pode validar com `inventoryService.hasStock(codigo, qtd)`.
3. Mais vendidos (E.1 lê as vendas): o E.2 implementa `InventoryService.SalesSource` (lista de código + quantidade
   dos itens vendidos, a partir do SaleRepository dele) e passa ao construtor do InventoryService.
   O DashboardService pode chamar `inventoryService.topSelling(n)`.
4. Criar `InMemoryProductRepository` e `InMemoryStockMovementRepository` UMA vez e compartilhar entre os serviços.

## Executar (sem Maven; JDK 17+)
    mkdir -p target/classes target/test-classes
    javac --release 17 -encoding UTF-8 -d target/classes $(find src/main -name '*.java')
    javac --release 17 -encoding UTF-8 -cp target/classes -d target/test-classes src/test/java/br/com/supermercado/*.java
    java -cp target/classes:target/test-classes br.com.supermercado.E1Demo
Windows (PowerShell):
    mkdir target\classes, target\test-classes
    javac --release 17 -encoding UTF-8 -d target/classes (Get-ChildItem -Recurse src/main -Filter *.java).FullName
    javac --release 17 -encoding UTF-8 -cp target/classes -d target/test-classes (Get-ChildItem src/test -Recurse -Filter *.java).FullName
    java "-Dfile.encoding=UTF-8" -cp "target/classes;target/test-classes" br.com.supermercado.E1Demo
